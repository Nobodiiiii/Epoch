审阅范围包括共享协议与存储层、主机协调器、五个 Forge 版本的主要适配路径、启动与实例管理脚本。主要关注状态交接、持久化一致性、世界生命周期、线程阻塞、资源预算和职责划分。

测试代码、测试结果、测试覆盖和补充测试建议全部排除，不作为本报告的判断依据或整改项目。未执行游戏或桌面 UI 自动化，未读取图片作为视觉输入。本文区分代码可确认的事实与由调用链推导出的风险，不将静态推断描述为已经观察到的运行故障，也不提供未经测量的性能收益数字。

### 哈希校验的强制约束

**明确禁止重复性的、不必要的、高性能压力的、触发条件过于频繁的哈希校验。** 此约束适用于现有实现的整改和后续新增功能，不能以“完整性保护”或“放到后台”为由绕过。

具体要求如下：

1. 禁止以每 tick、每帧、每次方块访问、每次区块加载阶段、每次修订查询或每次缓存查询为触发条件，反复读取同一内容并计算哈希。
2. 禁止用全文件、全目录、全规则包或全 JAR 哈希作为常规轮询探测机制。规则缓存或投影缓存命中时，不得重新读取原始内容进行哈希或全量字节比较。
3. 禁止在服务器线程和渲染线程执行大文件或成批内容哈希。转移到后台仍须满足去重、队列容量、CPU 时间和 I/O 预算要求，不能通过无限排队、扩大并发或高频轮询转移性能压力。
4. 必要校验必须有明确的数据边界和必要性，例如新对象首次接纳、实际内容变更后的发布，或用户明确发起的完整性检查。同一不可变内容版本的并发请求应合并，已完成的校验结果应复用。
5. 元数据查询应返回修订号、对象标识、规则代次等元数据，不得隐式升级为内容读取和哈希校验。新对象的必要校验由独立任务完成，调用方等待并复用其结果，不得在后续阶段重新计算。
6. 代码与规则指纹优先在构建、安装或显式重载时生成。运行期使用已发布的不可变版本标识；后台变化通知只负责请求重载，不直接触发整批重复哈希。
7. 完整性巡检如确有需要，应作为独立、低频、可取消且受预算约束的工作，不进入正常游玩热路径。不得默认持续扫描整个权威仓库。

这些要求不禁止确有必要的内容寻址和完整性保护。实现应通过不可变对象、校验结果复用和明确的更新边界达到目的，而不是以反复校验替代状态管理。

## 2. 总体判断

现有架构的基本方向合理：不同 Minecraft 版本由独立进程原生运行，共享层保存跨版本权威数据，版本适配器负责注册表、方块状态、NBT 与原生区块的转换，主机协调窗口和切换。

值得保留的设计包括：

- 单写者租约与修订前置条件，用于阻止过期实例覆盖权威数据。
- 不可变区块对象、提交日志和原子替换，降低进程中断时出现部分发布的风险。
- 对无法安全表示的内容保留原始状态和载荷，避免静默丢弃数据。
- 区分目标准备与最终交接，使目标冷启动期间源实例仍可运行。
- 限制脏数据和卸载快照的保留规模，并在无法安全恢复区块时拒绝直接生成替代地形。

优先整改方向是补齐运行模式、切换事务和重启检查点的一致性边界，再处理世界会话生命周期，随后削减同步保存、重复读取及校验开销。职责收敛应围绕这些边界逐步进行。

### A01：流式默认开关与旧版底层钩子不一致

**代码事实**

AutoRuntime.streamingEnabled() 对普通启动默认启用流式模式。1.12.2 的 StreamingTransformer 使用 Boolean.getBoolean("epoch.streaming")，未显式提供该属性时直接跳过全部转换。1.7.10 的区块提供器加载钩子和原生保存限流钩子也依赖显式属性，而其他部分钩子仍会注入。

**触发条件与影响**

普通启动未传入 -Depoch.streaming=true 时，上层可以启用流式世界，但底层必需钩子不完整。由此可能缺失区块恢复或后续编辑的脏数据跟踪，并在重载、提交或跨版本恢复时出现共享状态滞后及修订冲突。

**整改建议**

- 在类转换之前确定统一的运行模式，所有层使用同一默认值和同一配置语义。
- 避免仅在游戏初始化后修改属性，因为已经完成的类转换不会因此自动重新执行。
- 将必要钩子的安装结果作为运行能力显式登记；进入世界前检查能力，缺失时拒绝启用流式模式并给出原因。

**代码依据**：[默认开关](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/AutoRuntime.java:58)、[1.12.2 转换入口](D:/Files/Epoch/forge112/src/main/java/dev/epoch/core/StreamingTransformer.java:15)、[1.7.10 转换条件](D:/Files/Epoch/forge1710/src/main/java/dev/epoch/core/StreamingTransformer.java:16)。

### A02：提交后的交接异常仍尝试直接恢复旧写入者

**代码事实**

目标 StreamingWorld.resume() 在完成准备后转移租约。主机随后仍需等待 READY 回复并写入 session.json。主机 switchTo() 的异常路径没有区分租约是否已经转移，会冻结目标，再向源实例发送 resume。源实例按旧 epoch 校验所有权，无法通过此检查。

**触发条件与影响**

目标已经取得租约，但 READY 回复超时、状态发布失败或主机保存会话失败时，通用回退路径无法恢复源实例。当前所有权检查仍能阻止第二个写入者，问题在于缺少与提交点相匹配的恢复路径。

**整改建议**

- 以租约转移作为唯一交接提交点，持久化事务 ID、源与目标、阶段及提交后的所有者。
- 提交前失败允许恢复源实例；提交后失败应先读取持久化事务与所有权，确认目标状态并完成后续步骤。
- 若提交后需要返回源版本，应从当前权威实例重新导出并执行反向交接，不能直接恢复旧内存状态。
- 命令与应答绑定事务 ID，重复命令复用既有结果，不重复执行副作用。
- 保留现有过期租约拒绝逻辑，不能通过放宽 epoch 校验掩盖恢复流程缺失。

**代码依据**：[主机交接与回退](D:/Files/Epoch/host/EpochHost.java:505)、[恢复时所有权检查](D:/Files/Epoch/forge120/src/main/java/dev/epoch/StreamingWorld.java:546)、[租约提交点](D:/Files/Epoch/forge120/src/main/java/dev/epoch/StreamingWorld.java:579)。其他版本适配器也存在同类所有权流程。

### A03：重启检查点没有固定对应的全世界地形版本

**代码事实**

StreamCheckpoint 保存快照哈希、世界 ID、源实例及租约 epoch，没有保存可解析历史区块状态的索引根或修订集合。区块写入队列在游玩期间持续推进权威数据，SavedWorld 则单独发布玩家及附近区域快照。重启授权会使用当前存储租约重新绑定旧保存快照。

**触发条件与影响**

玩家检查点发布后，部分区块已产生更晚的提交，而新的玩家检查点尚未发布，此时发生异常退出，恢复流程可能组合旧玩家状态与新地形状态。

例如，保存时物品位于背包，之后玩家把物品放入该快照范围外的箱子。若箱子区块已提交而玩家尚未再次保存，重启可能同时恢复旧背包和较新的箱子内容。此处是由存储与恢复边界推导的风险，不代表已观察到该故障。

**整改建议**

- 建立统一检查点，将玩家、环境与可恢复的不可变地形索引根绑定到同一提交边界。
- 区分游玩中的工作状态与已发布检查点，恢复时明确选择同一边界下的全部数据。
- 仅新增一个全局 revision 数字不足以恢复历史状态；需要保留并解析该修订对应的区块对象引用。
- 在检查点和进行中的事务不再引用某个对象之前，不得回收该对象。
- 检查点应复用已有对象标识及校验结果，禁止为创建检查点重新哈希整个世界。

**代码依据**：[检查点结构](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/StreamCheckpoint.java:12)、[保存发布](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/SavedWorld.java:22)、[重启授权](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/SavedWorld.java:35)、[持续区块提交](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/ChunkWriteQueue.java:90)。

### A04：世界会话与客户端进程生命周期耦合

**代码事实**

AutoRuntime 使用静态 attempted 控制一次性启动，并在首次创建 seed 时记录世界名称。主机主要检查源进程是否存活。世界停止时 StreamingWorld 清理自身 Context，但没有对应的 AutoRuntime 世界会话重建流程。

**触发条件与影响**

在同一客户端退出存档 A 再进入存档 B 后，旧会话、seed 和预热目标仍可能属于 A。世界 ID 校验可以阻止跨世界错误导入，但无法替代旧会话的退出与新会话的建立，可能导致目标复用失败或切换持续被拒绝。

**整改建议**

- 区分进程级实例身份与世界级会话身份，不让一次性 attempted 同时承担两种生命周期管理。
- 世界卸载时结束或解除旧协调会话，处理属于该世界的预热实例与未完成任务。
- 新世界进入时创建新的会话代次，并重新绑定 worldId、seed 和目标列表。
- IPC 命令明确携带会话、世界和事务身份；旧世界命令在新会话中失效。

**代码依据**：[一次性启动逻辑](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/AutoRuntime.java:103)、[源进程存活判断](D:/Files/Epoch/host/EpochHost.java:381)、[世界停止清理](D:/Files/Epoch/forge120/src/main/java/dev/epoch/StreamingWorld.java:860)。

### A05：自动保存路径承担过多同步工作

**代码事实**

保存回调依次刷新区块、导出附近区域、再次刷新并发布快照，随后执行 prepareSavedWorlds()。该方法启动 Python，并在调用线程最多等待 30 秒。Python 会重新发现实例、检查进程并扫描存档。默认快照导出还会遍历 64×64×256，即 1,048,576 个方块位置。

**影响**

这些工作直接延长保存时服务器线程的停顿。30 秒是代码中的等待上限，不是本报告测得的实际耗时；实际路径还包含状态捕获和其他 I/O。

**整改建议**

- 服务器线程只执行必须与原生世界一致的捕获及提交边界操作。
- 将已经捕获的不可变数据交给有界后台队列压缩、写入和发布，并保持玩家与地形的统一检查点语义。
- 将存档入口准备从保存关键路径移出，仅在首次绑定或配置变化时执行，并合并同一世界的重复请求。
- 流式交接逐步改用玩家与环境快照加区块引用，复用已经提交的地形，避免每次保存和切换都重新全区域捕获。
- 后台化不能扩大队列或并发到无界，也不能在快照尚未完整发布时将其标记为可恢复。

**代码依据**：[保存调用链](D:/Files/Epoch/forge120/src/main/java/dev/epoch/StreamingWorld.java:513)、[全区域导出](D:/Files/Epoch/forge120/src/main/java/dev/epoch/Epoch.java:517)、[同步等待外部进程](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/AutoRuntime.java:43)、[存档入口扫描](D:/Files/Epoch/scripts/prepare_saved_worlds.py:10)。

### A06：修订和缓存查询包含重复内容校验

**代码事实**

ChunkStore.revision() 名义上查询修订，实际上读取整个压缩对象并计算哈希。区块 loading、decoded、loaded 等阶段存在重复修订查询。ChunkStore.content() 即使命中解码缓存，也先读取文件并进行全量字节比较。

CompatibilityRules.load() 在命中缓存之前会读取规则文件并计算摘要；ProjectionCache.stamp() 会进入这条路径。代码指纹首次计算还可能遍历和读取安装目录中的多个模组 JAR。

**影响及约束判断**

这些路径把元数据访问、缓存访问和完整性校验绑定在一起，导致相同内容被重复读取或计算。缓存仅节省部分解码工作，没有消除 I/O 和校验成本。其中重复、频繁触发的哈希行为违反第 1 节的明确约束，不能作为默认安全策略保留。

**整改建议**

- 修订查询仅读取小型索引元数据；返回修订和对象标识，不隐式读取对象内容。
- 每个不可变对象版本只安排必要的接纳校验任务；并发加载按对象标识合并，后续阶段复用已验证结果。
- 解码缓存命中时直接复用受管理的不可变内容或安全副本，禁止重新读盘并全量比较。
- 将规则解析与指纹生成移到显式重载或受控变更处理阶段，正常查询只读取已发布的规则版本。
- 将代码指纹优先移到构建或安装阶段，运行期读取版本清单，避免首次区块访问时扫描全部 JAR。
- 若需要检查外部文件损坏，使用独立且受预算约束的巡检或显式操作，不恢复每读一次就计算一次哈希的方案。

**代码依据**：[修订查询](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/ChunkStore.java:132)、[缓存命中前读取原文件](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/ChunkStore.java:283)、[区块加载中的重复查询](D:/Files/Epoch/forge120/src/main/java/dev/epoch/StreamingWorld.java:326)、[规则加载](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/CompatibilityRules.java:89)、[投影指纹入口](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/ProjectionCache.java:16)。

### A07：长期运行缺少完整的资源回收与预算策略

**代码事实**

ChunkStore 明确保留全部历史对象，SavedWorld 每次发布生成新的检查点文件。读取执行器没有显式任务队列容量；incoming 的数量限制不等同于执行器待处理任务的容量限制。预热管理没有整体并发或内存预算，目标启动参数统一包含 -Xmx3G。

**影响**

持续修改已有区块也会累积历史对象，磁盘增长不只与探索面积有关。慢磁盘、源区块请求阻塞或大量实例预热可能累积排队及内存压力。此处不将各进程的最大堆配置相加后视为实际已占用内存。

**整改建议**

- 在 A03 的引用关系明确后，按当前索引、保留检查点、进行中的事务和读者引用回收旧对象。
- 回收过程采用增量和预算控制，不通过反复全库哈希判断对象是否仍被引用。
- 对读取队列增加容量、请求去重、取消与背压；队列满时限制扩张，保持已有权威数据可恢复。
- 对预热增加并发数、总资源预算和空闲释放策略，允许用户主动释放已预热实例。
- 区分可淘汰缓存与权威数据，不能仅按玩家距离删除世界内容。

**代码依据**：[历史对象保留](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/ChunkStore.java:168)、[检查点文件生成](D:/Files/Epoch/src/shared/java/dev/epoch/bridge/SavedWorld.java:22)、[读取执行器](D:/Files/Epoch/forge120/src/main/java/dev/epoch/StreamingWorld.java:80)、[预热任务管理](D:/Files/Epoch/host/EpochHost.java:279)、[目标内存参数](D:/Files/Epoch/scripts/launch_epoch.py:111)。

### A08：每 tick 强制覆盖用户显示设置

**代码事实与影响**

客户端 tick 持续将 FOV、视角晃动和失焦暂停设为固定值；部分版本还强制第一人称或限制 FOV 动态效果。相关赋值没有限定在最终交接期间，因此会持续覆盖正常游玩设置。

**整改建议**

仅在需要时临时接管与交接有关的设置，保存原值并在接管结束时恢复。对必须长期限制的设置建立明确、可配置的运行策略，避免在每 tick 无条件赋值。

**代码依据**：[1.20.1 客户端设置](D:/Files/Epoch/forge120/src/main/java/dev/epoch/Epoch.java:235)、[1.12.2 客户端设置](D:/Files/Epoch/forge112/src/main/java/dev/epoch/ClientHooks.java:49)、[1.16.5 客户端设置](D:/Files/Epoch/forge116/src/main/java/dev/epoch/ClientHooks.java:104)。

### A09：运行环境依赖个人机器路径

**代码事实与影响**

启动脚本直接写死 Java 8 与 Java 17 的安装位置，部分构建配置也绑定个人目录。换机器或调整 JDK 安装位置时，需要修改多个文件，运行时环境与仓库实现耦合。

**整改建议**

引入统一运行时配置与版本清单，明确配置覆盖、已发现运行时和错误反馈的优先级。JDK、原生组件、模组产物及其协议版本在准备阶段解析为启动清单，主机消费该清单。环境发现不得在每次 tick、状态查询或区块操作中重新执行。

**代码依据**：[启动脚本中的 JDK 路径](D:/Files/Epoch/scripts/launch_epoch.py:10)、[旧版工具链配置](D:/Files/Epoch/forge1710/gradle.properties:3)。

## 4. 架构职责收敛

目前共享层已经隔离了部分 Minecraft 依赖，但五份 StreamingWorld 仍重复实现上下文管理、租约恢复、保存检查点、脏数据处理与生命周期流程。主机同时管理窗口、进程、预热、命令、切换和故障恢复。建议沿业务边界逐步收敛，而不立即重写所有原生适配代码。

| 层次 | 建议集中承担的职责 | 应保留的边界 |
|---|---|---|
| 共享核心 | 世界会话、切换状态机、事务身份、租约流程、任务预算和恢复策略 | 不直接依赖 Minecraft 类或 Win32 窗口接口 |
| 存储层 | 不可变对象、区块索引、提交日志、检查点、引用保留和增量回收 | 不负责玩家传送或修改原生世界 |
| 兼容转换层 | 状态规则、载荷迁移、原始信息保留、不可变规则版本 | 规则重载与查询分离，查询不执行文件哈希 |
| 版本适配器 | 原生区块捕获和应用、NBT、注册表、光照、Forge 生命周期钩子 | 原生访问遵守版本对应的线程要求；通用事务流程交给共享核心 |
| 主机 | 进程和窗口管理、能力协商、驱动交接事务、报告运行状态 | 通过明确协议确认提交结果，不猜测写入者状态 |
| 启动与部署层 | 实例发现、环境配置、产物安装、启动清单和存档入口准备 | 移出游戏 tick 和保存关键路径，重复请求合并 |

优先抽取变化频率低、语义一致的会话和所有权逻辑。原生区块读写、光照及旧版 ASM 钩子继续由版本模块负责，避免为统一接口引入大量版本条件分支。

流式模式的交接与保存应逐步复用区块权威数据。固定区域 Snapshot 可作为旧协议兼容入口保留，避免让完整区域捕获和区块存储长期成为两套并行的主要实现。

## 5. 建议实施顺序

| 阶段 | 工作内容 | 完成后的实现状态 |
|---|---|---|
| 第一阶段 | A01；立即停止 A06 中违反哈希约束的高频重复路径 | 运行模式与必要钩子一致；修订和缓存查询不隐式反复读盘校验 |
| 第二阶段 | A02、A03 | 交接以明确提交点恢复；重启引用统一的玩家、环境和地形检查点 |
| 第三阶段 | A04；抽取共享会话与所有权流程 | 进程身份与世界会话分离；五版共享同一事务语义 |
