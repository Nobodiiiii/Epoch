# Epoch 方块兼容架构与实施方案

## 1. 目标与完成标准

支持 1.7.10、1.12.2、1.16.5、1.18.2、1.20.1。每个原版方块状态必须有
可复现的去向：直接支持、规则转换、保留占位；任何未覆盖情况必须给出原因。
“所有状态有处理结果”不等同于“所有新方块在老版本里拥有原生行为”。不存在的
方块不能通过改名获得等价实现，必须保留原始状态和方块实体 NBT。

## 2. 数据流与职责

```
版本原生状态 / metadata + 原生 NBT
  → 版本适配器解码
  → CanonicalBlockState（稳定名称、属性、原始 SNBT、legacy 标记）
  → 尝试直接表示，失败后进入规则引擎（目标版本、目标模组版本、目标注册表）
  → 校验转换后的全部属性
  → 目标原生状态
  → 原有方块实体类型与 NBT 往返检查
  → 放置正常方块，或携原始数据的未知方块
```

共享模块保持 Java 8 兼容，不依赖任何 Minecraft 类。版本模块只负责注册表、
NBT 和原生状态操作。现有 Snapshot schema 1 和原始 SNBT 保持兼容；不以 JSON
数值重写 NBT，避免长整型、数组、数值类型及未知字段丢失。

新旧客户端或占位方块可能携带比导出版本更早/更新的数据，因此第一版规则
按目标能力和明确的输入属性匹配，不将 `Snapshot.version` 当作原始数据版本。
同理，不能将当前导出客户端的模组列表当作未知方块的原始模组版本。

## 3. 四个兼容等级

| 等级 | 判定 | 第一版执行策略 |
|---|---|---|
| EXACT | 原名称及全部输入属性被支持 | 直接放置，继续校验 NBT |
| CONVERTED | 显式声明语义等价的规则，输出通过注册表校验 | 放置，记录规则 ID |
| PRESERVED | 需要额外保存无法表达的信息 | 通过已有未知方块承载原始数据 |
| SUBSTITUTE | 近似外观/行为 | 第一版不启用，防止误当作无损兼容 |

未知方块是受支持的保留结果，不是默认空气或随机替代方块。销毁占位方块
即删除内容；不会从脱离世界的旧位置记录复活它。

## 4. 规则系统

### 4.1 分发与加载

- 内置原版包随所有适配器打包。
- 用户/整合包规则位于项目 `.minecraft/epoch/compatibility/packs/*.json`，
  可通过 `epoch.compatibilityDir` 指定其他目录。
- 每次导入前一次性读取、校验、冻结规则集；同一次导入不会混用文件修改前后的规则。
- Java 模组通过 ServiceLoader 提供 `BlockCompatibilityProvider`。
- 未知字段、重复 ID、不受支持的安全等级、规则冲突必须报告，不静默忽略。
- 文件名排序不决定冲突胜者。先比较显式 priority；同优先级同时匹配则拒绝
  该状态并列出冲突规则。一次转换只执行一个规则，避免隐式规则链和循环。

### 4.2 匹配与转换

每条声明式规则明确列出目标 Minecraft 版本、方块 ID 集合，以及必要的目标
模组版本和输入属性条件。允许 ID 映射、属性改名、受限值映射、带预期值的
属性删除、显式属性补全。禁止通配所有命名空间或自动删除未知属性。

目标已有同名属性时不能应用“缺失属性省略”规则。属性改名覆盖其他现有属性
必须拒绝。目标方块缺失、属性不存在或取值非法，即使规则匹配也必须退回保留。

用户规则声明 `safety=equivalent` 是作者的语义承诺，不是引擎能自动证明的事实。
JSON 只处理状态；带 NBT 的方块仍经过原有严格 NBT 往返检查。状态转换成功
不能绕过容器/机器的数据校验。

### 4.3 模组 Java 扩展

Java provider 返回与 JSON 相同的经过验证的规则对象，适用于动态生成大量
机器变种规则，避免反射访问 Minecraft 内部类或复制导入器。模组版本必须按
实际目标加载器清单匹配；版本信息缺失时不满足受版本约束的规则。

复杂机器 NBT 迁移另设后续接口，必须提供原始数据保留与逆变换证据。在该
协议落实前保持占位，不能以通用字段重命名器猜测能量单位或库存语义。

## 5. 原版覆盖与注册表工具

各版本导出真实注册表快照：版本、模组清单、原生合法状态的统一描述、原始
SNBT。现代版本遍历 state definition；legacy 版本遍历可表示的 metadata 并
使用已有 flattening 表，无法解释的 metadata 带来源标记保留。

第一批规则：旧树叶非含水状态、草径/土径命名迁移、旧 grass_path 与统一名称
的双向落地。其余原版状态先通过实际注册表审计明确列出，再添加有证据的规则。
NBT、邻居推导属性和多方块结构的差异不得为了提高百分比被自动丢弃。

## 6. NBT 与多方块结构

现有新鲜方块实体构造、类型校验、导入再序列化和字段保留检查继续作为必要
条件。诊断同时记录状态失败和方块实体失败，避免“状态完全支持”掩盖 NBT 丢失。

后续扩大原生可用范围按告示牌、容器物品、床/门、红石/流体、模组机器依次
进行。每类需要两版本真实世界 fixture、往返比较和玩家修改后的验证。
单个状态规则不能承诺床的另一半、箱子配对或跨共享区域边界结构已完整迁移。

## 7. 正常外观的可逆降级（启用门槛）

不能仅依赖“位置＋方块 ID 相同”恢复旧数据。未来实现必须具备：

在这组条件通过前，不为普通方块引入半完成的旁路恢复表；需要保存额外数据
时统一使用已存在的未知方块。这是第一版明确的安全边界。

## 8. 本次实施与验证清单

本次不声称已重现旧版本不存在的新方块行为，也不把真实世界 fixture 尚未
通过的类别标成完全兼容。后续规则的验收依据是覆盖报告中的具体缺口。

## 9. 落地结果

状态规则层已接入三个现代版本；五个版本都有原生注册表导出和审计工具。
首批原版规则覆盖树叶、铁轨的非含水属性，草径/土径改名，以及炼药锅水位表示。
全量审计发现并修复了旧头颅映射中的非法占位名称。

验证范围和实际缺口见 [覆盖报告](COMPATIBILITY_COVERAGE.md)，模组作者入口见
[模组接入指南](MOD_COMPATIBILITY.md)。普通外观的有损降级、机器 NBT 迁移接口及
世界行为 fixture 仍按第 6、7 节的验收条件推进，不属于已经验证的能力。
